## Compound Learning — Bad Patterns

This file grows over time. When a bad pattern is caught in review, add it here so it is never repeated.

<!-- Format: - **Pattern:** description | **Why it's bad:** reason | **Do this instead:** correct approach -->

- **Pattern:** Using `bg-brand-navy` or `text-brand-navy` in Tailwind classes | **Why it's bad:** `brand-navy` is not a registered token — Tailwind silently produces no colour, so dark sections appear transparent/white | **Do this instead:** Use `bg-brand-primary` or `bg-brand-primary-900` (both resolve to #012B43 navy)
- **Pattern:** Importing `{ motion }` from `framer-motion` directly in a Next.js App Router `page.tsx` Server Component | **Why it's bad:** framer-motion is client-only — calling it from the server crashes at build with "createMotionComponent() from the server" | **Do this instead:** Extract all motion-using JSX into a separate `*Content.tsx` file with `"use client"` at the top, then import that from the page
- **Pattern:** Importing `{ Linkedin }`, `{ Instagram }`, or `{ Facebook }` from `lucide-react` | **Why it's bad:** lucide-react v1.x removed social brand icons — they are not exported and cause a TypeScript build error | **Do this instead:** Use inline SVG paths for social icons (standard brand SVGs from simpleicons.org)
- **Pattern:** Removing `typescript: { ignoreBuildErrors: true }` from `apps/payload/next.config.ts` | **Why it's bad:** Payload CMS 3.x ships type declarations that conflict with React 19's ReactNode — the build fails with "Type 'ReactElement' is not assignable to type 'ReactNode'" — this is a known upstream Payload bug, not our code | **Do this instead:** Keep `typescript: { ignoreBuildErrors: true }` alongside any other config changes to `apps/payload/next.config.ts` until Payload fixes the upstream type issue
- **Pattern:** Setting `NEXT_PUBLIC_MEDUSA_URL` to an internal Docker hostname like `http://medusa:9000` | **Why it's bad:** NEXT_PUBLIC_* vars bake into the browser bundle at build time — browsers cannot resolve Docker internal hostnames, breaking all Medusa API calls | **Do this instead:** Use the public-facing URL that browsers can reach (IP testing: `http://169.239.180.49/api`, production: `https://suzanneravenall.com/api`) — the Medusa JS SDK appends `/store` or `/admin` to this base URL, and Nginx rewrites `/api/store/*` → `/store/*`
- **Pattern:** Setting `PAYLOAD_URL` to the direct Payload port URL like `http://169.239.180.49:3001` | **Why it's bad:** Payload's `serverURL` must match the URL browsers actually use to access it — using the direct port bypasses Nginx basePath routing and causes broken login redirects (it does NOT cause hydration #418 — that was a separate nested-`<html>` bug, see next entry) | **Do this instead:** Use the Nginx-proxied URL: `http://169.239.180.49/cms` (IP testing) or `https://suzanneravenall.com/cms` (production)
- **Pattern:** Rendering `<html>`/`<body>` in the root `apps/payload/src/app/layout.tsx` when the `(payload)` route group already provides Payload's `RootLayout` | **Why it's bad:** Next.js wraps route-group routes in the root layout, so the admin ships TWO nested `<html>` tags — the browser collapses them and the client DOM diverges from the server DOM, throwing React hydration error #418. The hydration crash can also break the login form's server action, so login bounces back even on a fresh/incognito load | **Do this instead:** Make the root `app/layout.tsx` a pass-through (`return children`) so Payload's `RootLayout` is the SOLE owner of `<html>/<body>`. The only root-level page just `redirect()`s, so it needs no html/body. Verify: `curl -s <host>/cms/admin/login | grep -oE '<html[^>]*>' | wc -l` must return `1`. (Fixed in commit e7139ee)
- **Pattern:** Not updating the Payload healthcheck in docker-compose.yml when adding `basePath: '/cms'` to next.config.ts | **Why it's bad:** The healthcheck tests `http://localhost:3001/admin` but basePath moves the admin to `/cms/admin` — healthcheck always fails, Docker marks the container unhealthy, and Nginx refuses to start | **Do this instead:** Update the healthcheck to `curl -f http://localhost:3001/cms/admin` whenever basePath is set or changed in Payload's next.config.ts
- **Pattern:** Using `md:` responsive prefix in Tailwind classes (e.g. `md:py-32`, `md:text-6xl`) | **Why it's bad:** The project design system only uses `sm:` (640px) and `lg:` (1024px) breakpoints — `md:` (768px) is explicitly excluded to keep the responsive system simple and consistent | **Do this instead:** Use `lg:` for tablet-and-up scaling (e.g. `py-20 lg:py-32`, `text-4xl lg:text-6xl`)
- **Pattern:** Using `<Script src="..." strategy="afterInteractive" />` from `next/script` in Next.js 15 + @types/react 19.x | **Why it's bad:** The `src` prop type conflicts with the resolved `ScriptHTMLAttributes` in this dependency combination — build fails with "Property 'src' does not exist on type ScriptProps" | **Do this instead:** Use a native React `<script async src="..." />` element for external script URLs — React 19 handles async scripts natively. Keep `next/script` only for inline `<Script id="..." strategy="afterInteractive">` blocks
- **Pattern:** Defining `MedusaProduct` type separately in multiple shop components (ShopCatalogueContent, ProductCard, ProductPageContent) | **Why it's bad:** Three structurally identical type definitions drift over time — one gets updated, others don't, causing subtle bugs | **Do this instead:** Define once in `apps/web/types/medusa.ts` and import from there
- **Pattern:** Using a two-stage Dockerfile for Medusa v2 where the runtime stage only copies `.medusa/server` and `medusa-config.js` | **Why it's bad:** Medusa v2's `medusa build` puts the admin UI in `.medusa/server/public/admin/` but does NOT compile backend TypeScript — the runtime loads TypeScript via ts-node, so the `src/` directory and devDependencies (ts-node) are required in the runtime image | **Do this instead:** Use a single-stage Dockerfile that installs all deps (including devDeps), copies all source, runs `medusa build`, then `mkdir -p ./public && cp -r .medusa/server/public/admin ./public/admin` to place the admin bundle where the server expects it (`ADMIN_RELATIVE_OUTPUT_DIR = ./public/admin`)
- **Pattern:** Medusa `DATABASE_URL` pointing to internal Docker Postgres without `?sslmode=disable` | **Why it's bad:** The pg driver may attempt SSL against the Docker-internal Postgres container which has no SSL configured — all module migrations fail with "The server does not support SSL connections" | **Do this instead:** Append `?sslmode=disable` to `MEDUSA_DATABASE_URL` in `infra/.env` when pointing to the local Docker Postgres container
- **Pattern:** Adding a 301 redirect for `/checkout` → `/shop` in next.config.mjs redirects() (from WooCommerce migration work) | **Why it's bad:** The new platform has a real checkout page at `/checkout` — Next.js redirects fire before page routing, so the redirect permanently blocks the checkout page from loading | **Do this instead:** Only redirect the old WooCommerce `/basket` path; leave `/checkout` and `/cart` unreserved for the new pages. RECURRED 2026-07-28 with `/events/:slug*` → `/contact` blocking the new `/events` page: `:slug*` matches ZERO segments, so it captures the bare path too — use `:slug+` when the bare path is (or may become) a real page
- **Pattern:** Adding `NEXT_PUBLIC_*` env vars to the web app without declaring them as `ARG`/`ENV` in the Dockerfile and as `args:` in `docker-compose.yml` | **Why it's bad:** `NEXT_PUBLIC_*` vars are baked into the JS bundle at build time — if they are not passed to the Docker builder as build args, they are empty strings in production even if they exist in the container's runtime env | **Do this instead:** For every `NEXT_PUBLIC_*` var, add `ARG VARNAME` + `ENV VARNAME=$VARNAME` in the Dockerfile builder stage AND `args: VARNAME: ${VARNAME}` in docker-compose.yml's `build.args` block
- **Pattern:** Leaving the corepack-managed yarn shim (`/usr/local/bin/yarn`) in the Docker build image for the web app | **Why it's bad:** Next.js 15 detects the yarn shim via PATH and attempts to auto-install `@types/react` through it; corepack 1.x misreads `"packageManager": "npm@x.x.x"` as a yarn identifier and aborts the build | **Do this instead:** Add `RUN rm -f /usr/local/bin/yarn /usr/local/bin/yarnpkg` in the Dockerfile builder stage before running `turbo run build`
- **Pattern:** Using `moduleResolution: "bundler"` in `apps/medusa/tsconfig.json` when `module` is set to `"CommonJS"` | **Why it's bad:** TypeScript 5 rejects `moduleResolution: "bundler"` unless `module` is `"preserve"` or ES2015+; with CommonJS it throws TS5095 | **Do this instead:** Use `"module": "Node16"` and `"moduleResolution": "Node16"` together — these support subpath exports (needed for `@medusajs/framework/utils`) and are compatible with each other. Since Medusa uses esbuild/swc for actual compilation and `noEmit: true`, the module setting only affects type resolution
- **Pattern:** Using `NODE_ENV !== 'production'` to bypass payment webhook signature verification | **Why it's bad:** Staging servers run with real Medusa data regardless of NODE_ENV — the bypass allows any attacker to POST a fake webhook and complete real carts without payment | **Do this instead:** Use a dedicated `PAYPAL_SANDBOX=true` env var and only bypass when BOTH `PAYPAL_SANDBOX=true` AND `NODE_ENV=development` — never bypass on staging
- **Pattern:** Not verifying that a payment orderId (from return URL) corresponds to the provided cartId in the capture endpoint | **Why it's bad:** An attacker with a valid approved orderId from their own low-value purchase can substitute a victim's cartId to complete an expensive cart for free (substitution attack) | **Do this instead:** After capture, read `custom_id` from the payment provider's response body (PayPal: `purchase_units[0].custom_id`) and assert it equals the cartId provided by the client before calling completeCart
- **Pattern:** Updating Medusa order metadata with only the new key (`{ metadata: { invoice_url: url } }`) without spreading existing metadata | **Why it's bad:** Medusa v2's `POST /admin/orders/:id` replaces the entire metadata object — all prior keys (payfast_payment_id, paypal_order_id, sage_document_number) are silently erased | **Do this instead:** Fetch the order first, then spread: `{ metadata: { ...order.metadata, invoice_url: url } }`
- **Pattern:** Using `@react-pdf/renderer` v3.x in a project with React 19 without adding it to `serverExternalPackages` and acknowledging the TypeScript JSX errors | **Why it's bad:** (1) react-pdf uses Node.js native binaries — Next.js webpack will fail to bundle it unless marked external; (2) react-pdf v3 types declare components as `React.Component<Props>` which is incompatible with React 19's stricter JSX type checking — `tsc --noEmit` produces TS2786/TS2607 errors on every JSX element | **Do this instead:** Add `serverExternalPackages: ['@react-pdf/renderer']` to `next.config.mjs`. The TypeScript errors are a known upstream React 19 type incompatibility — they are already covered by `typescript: { ignoreBuildErrors: true }` in `next.config.mjs` and do not affect the Docker build or runtime behaviour

- **Pattern:** Silently skipping webhook auth when the secret env var is missing (`if (webhookSecret) { verify } else { console.warn + skip }`) | **Why it's bad:** If the env var is accidentally unset in production (misconfiguration, missed deploy), the endpoint becomes fully open to any caller — same failure mode as the PayPal sandbox bypass and equally dangerous in staging | **Do this instead:** Treat a missing secret as a server configuration error: `if (!webhookSecret) return NextResponse.json({ error: 'Server configuration error' }, { status: 500 })` — fail loudly rather than degrade silently
- **Pattern:** Creating Medusa v2 products via the Admin API without an `options` array (even for single-variant products) | **Why it's bad:** Medusa v2 requires every product to have at least one option, and every variant to have a corresponding `options` array — missing these fields causes the create call to fail with "Product options are not provided for: [product title]" | **Do this instead:** Always include `options: [{ title: "Type" }]` on the product and `options: [{ value: "Membership" }]` (or the relevant value) on each variant — applies to all seed scripts and Admin API calls
- **Pattern:** Using `next.config.ts` (TypeScript) in `apps/payload` which has `"type": "module"` in its `package.json` | **Why it's bad:** Next.js 15's config loader fails to load TypeScript config files in ESM packages (packages with `"type": "module"`) — build fails with `⨯ Failed to load next.config.ts` | **Do this instead:** Use `next.config.mjs` (plain JavaScript ESM) — drop the `import type { NextConfig }` line and the `: NextConfig` type annotation; the config object is identical, Next.js loads `.mjs` without needing a TypeScript transform
- **Pattern:** Setting `ENV NODE_ENV=production` before the `RUN npx turbo run build` step in a Payload/Next.js Dockerfile | **Why it's bad:** Some Next.js and Payload internals gate behavior on NODE_ENV during the build phase — setting production mode before the build can block config loading or plugin registration | **Do this instead:** Place `ENV NODE_ENV=production` on the line AFTER the build `RUN` command in the builder stage; the runner stage always gets its own `ENV NODE_ENV=production`
- **Pattern:** Adding `"next": "X.Y.Z"` override to root `package.json` without regenerating the lockfile afterward | **Why it's bad:** `npm ci` uses the EXACT lockfile — if the lockfile still has a workspace-local `apps/web/node_modules/next@OLD` entry from before the override, `npm ci` installs BOTH the overridden root version AND the stale workspace-local version. In Docker partial-workspace builds, two Next.js module instances cause the Pages Router `Html` guard check to fail during static generation with "should not be imported outside of pages/_document" | **Do this instead:** After adding or changing a version override in root `package.json`, immediately run `npm install` (or manually remove the stale workspace-local lockfile entry) so the lockfile reflects the override. Also declare the exact overridden version explicitly in the workspace's `package.json` (e.g. `"next": "15.3.9"` not `"^15.3.3"`) to prevent drift
- **Pattern:** Registering `@medusajs/file-local` (or any file storage provider) as a top-level module in `medusa-config.js` | **Why it's bad:** In Medusa v2, file-local is a PROVIDER, not a standalone module — `defineConfig` tries to access `.prototype` on its exports to find the module service class, gets `undefined`, and crashes with "Cannot read properties of undefined (reading 'prototype')" causing a Medusa crash-loop that takes the entire site down. Also: `@medusajs/file-local` is not a valid npm package for Medusa v2. | **Do this instead:** Use the nested provider pattern with the subpath exports bundled inside `@medusajs/medusa` — no extra package needed: `{ resolve: "@medusajs/medusa/file", options: { providers: [{ resolve: "@medusajs/medusa/file-local", id: "local", options: { upload_dir: "uploads", backend_url: (SITE_URL) + "/uploads" } }] } }`
- **Pattern:** Writing n8n workflow JSONs with `typeVersion` values higher than what the pinned n8n container version supports | **Why it's bad:** n8n node types are versioned — specifying e.g. `httpRequest typeVersion: 4.2` when the container only ships httpRequest up to V3 causes all workflow activations to fail with "Cannot read properties of undefined (reading 'description')" (n8n looks up the node type, gets undefined, then crashes reading `.description`). n8n 1.30.1 ships httpRequest up to V3; V4 was introduced in ~1.34. | **Do this instead:** Always check the n8n container version in `infra/docker-compose.yml` before writing workflow JSONs — use node typeVersions that are available in that version. As a rule, pin n8n to the latest stable (2.x) which supports all current node type versions including httpRequest V4.2, scheduleTrigger 1.1, set v3.4, wait v1.1. As of May 2026 stable is 2.20.9. Note: n8n moved from 1.x to 2.x versioning — there is no 1.48.4 tag on Docker Hub
- **Pattern:** Using `text-brand-accent` (DEFAULT, #1719F4) as text/icon colour on a dark background (`bg-gray-900`/`bg-gray-950`, `bg-brand-primary*`, or a darkened image overlay like `bg-gradient-to-br from-gray-900/80`) | **Why it's bad:** #1719F4 is dark and saturated — contrast against near-black is only ~2.5:1, well under the WCAG AA minimum of 4.5:1, so the text is genuinely hard to read. It looks fine in design mockups on white (~8.5:1) which is why it keeps slipping through review — the failure only shows up on dark sections and on hover states over photos (e.g. product/programme/topic cards where a CTA or category label turns `text-brand-accent` on `group-hover`). Found live 2026-07-29 in 14 image-hover card components (KI026 in KNOWN_ISSUES.md tracks the remaining ~400-instance sitewide sweep of static eyebrow labels on dark sections). | **Do this instead:** On dark backgrounds use `text-brand-accent-400` (#7578f7, ~5.8:1 contrast) instead of the bare `text-brand-accent`/`-600`. Reserve `bg-brand-accent`/`bg-brand-accent-600` for BUTTON FILLS only — white text on top of that background is fine. On white/light backgrounds the bare `text-brand-accent` is correct and should not be changed.
