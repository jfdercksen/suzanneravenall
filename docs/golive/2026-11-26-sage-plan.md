## (b) Sage item codes on the products

- **Where the code goes:** variant metadata `sage_item_code`, not the variant SKU field.
  - Three variants already hold Thinkific ids in `sku`.
  - Membership logic reads its own codes.
  - Overwriting `sku` risks the course enrolment.
- **Source:** infra/scripts/catalogue-parity/parity.csv (14 Oct map, new variant to old WooCommerce id), joined to the old shop's S-codes.
  - The old shop's codes come from its public product list, read again on the day.
  - 142 of 145 mapped variants get a code.
- **The gaps, checked by hand with Carla:**
  - the 3 unmatched variants;
  - products added since 14 Oct (149 published variants today);
  - the memberships, which are not in the map.
- **Script:** Medusa admin API.
  - Dry run first: a list of variant, product and S-code for Carla to check against her Sage item list.
  - Then the write: one variant at a time, metadata spread so no other key is lost (bad-pattern rule).
  - Read back afterwards.
- **Test:** unit test of the join (match, no match, duplicate code); the dry-run list itself is the acceptance check.
- **Effort:** half a day.
- **Risk:** low. Metadata only, reversible by removing the key.

## (a) Daily order list for Carla

- **What:** a Medusa scheduled job (pattern of apps/medusa/src/jobs/*), every working day at 07:00 SAST. It covers the previous working day; Monday covers Fri-Sun.
- **Content, per order:**
  - `SR-<order>` exactly as on the customer's PDF;
  - date;
  - customer name and email;
  - billing address or company where given;
  - each item with its Sage item code (from b), quantity and amount;
  - currency;
  - discount or voucher;
  - total;
  - payment method and gateway reference.
- **Format:** the mail body as a table, plus a CSV attachment for import or checking.
  - The mail says "Type SR-<order> in the invoice reference field".
  - On a day with no orders, a one-line mail, so a missing mail means a fault.
- **Excluded:** test orders (QA voucher), and cancelled or fully refunded orders. Refunds show in a second section, so Carla can credit an invoice she already raised.
- **Sending:**
  - through Brevo via the web app's internal email route, like the other staff mails;
  - recipient from a new env name `SAGE_ORDER_LIST_EMAIL`, Carla's address set by Johan, with a team Cc if wanted;
  - a failure goes to the staff alerter.
- **Customer data:** the list carries names, emails and amounts to Carla only. That is the same data she sees in Sage. The mail footer says it stays within the team.
- **Tests:**
  - window (Monday covers the weekend, a public holiday);
  - exclusions;
  - refunds section;
  - USD order;
  - voucher order;
  - empty day;
  - item without a code (shown as "no code, check").
- **Effort:** half a day to a day.
- **Live Monday:**
  - Yes, if built Friday or Saturday and medusa is deployed after the switch is stable.
  - Fallback for Mon 30 Nov only: we send Carla the list by hand from the shop admin.

## (c) The Sage build, in order

Against the new trial company. Each stage has unit tests with recorded Sage answers (not hand-written shapes, per the PayPal lesson in no-bad-patterns.md) and one sandbox call.

1. **OAuth 2.0 sign-in** (1 day).
   - Web route `/api/sage/oauth/callback`. It sits under `/api/`, not `api/auth`, so nginx sends it to Next.
   - State parameter checked; tokens stored encrypted server side (a new table with RLS, or Medusa's own store); refresh before expiry; a staff alert when refresh fails.
   - Connected once by an admin.
   - Until Sage issues the client details, sandbox basic auth stays behind the same interface, so stages 2-6 are not blocked.
2. **Customer** (0.5 day).
   - Find by email once, then remember the Sage customer id against the email in our own table.
   - The current code pages through every Sage customer on every order, the call pattern a reviewer will flag.
   - The rule (per customer, or one cash customer) follows Carla's Stock2Shop invoice.
3. **Invoice** (1 day).
   - Lines by Sage item code (from b), falling back to the income account with a warning when a code is missing.
   - The no-VAT tax type from config (`SAGE_TAX_TYPE_ID`), refusing to post if it is unset; never the 15% type.
   - Amounts in rand as Medusa holds them (no /100).
   - Inclusive prices.
   - Reference `SR-<order>`.
4. **Currency** (0.5 day). The rule from Carla's sample, one of:
   - a USD order to a foreign-currency invoice;
   - converted at the payment's rate;
   - a separate customer.
   Until decided, USD orders are held, not posted, with an alert.
5. **Skip if already in Sage** (0.5 day).
   - Before posting, look up an invoice with reference `SR-<order>`. If one exists (a hand invoice), record its number on the order and stop.
   - This is what makes hand invoices safe.
6. **Outbox and alerts** (0.5-1 day).
   - A `sage-invoice` job in the existing outbox (apps/medusa/src/automations): idempotency key per order, retries 1 m to 12 h, dead after that with one staff alert.
   - `AUTOMATION_SAGE` flag (off, shadow, code). Shadow builds the invoice and logs it without posting, so it can run on live orders before the key arrives.
   - The Sage number goes into order metadata, so the customer's PDF shows it.
   - The n8n call in order-placed.ts is removed.
7. **Refunds** (0.5 day, can follow): a credit note referencing the invoice, or an alert for Carla to raise one by hand.

**Total:** about 4-5 days of our work. Sage's review comes after stage 6 and its timing is theirs.

## (d) What Sage's reviewers will want to see in the sandbox logs

Inferred from their 12 May mail (they evaluate the sandbox call logs before a live key) and usual API review practice. Ask Sage for their checklist in the same mail.

| Test | Shows |
|---|---|
| New customer, one order, one item | Customer created once, invoice posted, no repeated lookups |
| Same customer, second order | Stored id reused, no customer search |
| Order with several items and a voucher | Line amounts and the discount add up to the order total |
| USD order | The agreed currency rule |
| Order already invoiced by hand (SR- reference exists) | One lookup, no post |
| Invalid data (unknown item code, unset tax type) | Refused before any call, no failed posts in their log |
| Sage answers 401, 429 or 500 | Back-off and retry, no tight retry loop; token refresh on 401 |
| Refund | Credit note, or no call |
| A day's volume | Calls per order stay small and steady (about 2-3), no polling |

Then send Sage the ready notice with the dates and order numbers of these runs.
